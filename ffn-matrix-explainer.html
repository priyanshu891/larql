FFN as Key-Value Memory

An interactive matrix walkthrough — see how a transformer's feed-forward block actually works.

W_gate: keys (pattern detectors)

Step 1 · Setup
Meet the four matrices
Imagine a tiny transformer with hidden size 4 and FFN width 5. Each row of W_gate is a "feature detector" — I've labeled them so you can see what they're tuned to.
x [1 × 4] · query
W_gate [5 × 4] · keys
W_up [5 × 4] · gains
W_down [5 × 4] · values
Key idea: Each row index i in W_gate, W_up, and W_down refers to the same feature. Feature i's key (W_gate row i) decides if it matches the input. Its gain (W_up row i) decides how loud. Its value (W_down row i) decides what it writes back into the residual stream.
Step 2 · Match
x · W_gate → "how well does each key match?"
We dot-product the input x with each row of W_gate. A high score means "this feature recognized something it cares about."
gate = x @ W_gate.T → gate[i] = dot(x, W_gate[i])

Step 3 · Decide firing strength
silu(gate) · up → "how strongly does each feature actually fire?"
Two things happen here. First, SiLU squashes the match scores: negative scores are killed (≈0), positive scores stay roughly themselves. This is the non-linearity. Then we multiply by the up projection (x @ W_up) — that's the gain knob that says "how loudly should this feature contribute?"
act = silu(gate) * up where up = x @ W_up.T

This is where non-linearity enters the model. If we skipped SiLU, the whole network would collapse into one big linear function — no matter how many layers we stacked. The orange glow shows which features fire. Most are near-zero — that's the sparsity LARQL exploits in its Walk FFN.
Step 4 · Read out values
act · W_down → the FFN's output
Each firing feature pulls its corresponding row out of W_down (its value vector) and adds it to the output, scaled by how strongly it fired. Features that didn't fire contribute nothing.
out = act @ W_down → out = Σᵢ act[i] · W_down[i]

The big picture: The FFN is a content-addressable memory. Input x is the query. W_gate stores keys. W_down stores values. The activation step decides which key-value pairs apply to this input. That's why LARQL says "the model is the database" — every row is a stored fact.
In LARQL terms
Why this matrix view matters
LARQL decompiles a real transformer into a queryable graph by treating each FFN row as a node. The Walk FFN optimization works because of a fact this demo makes obvious: most features don't fire on a given input.
How sparse is real FFN activation?
On Gemma-3 4B, only ~10 out of 10,240 features per layer fire strongly for a given token. Instead of a dense matmul against all 10,240 down-projection rows, LARQL does a KNN search on W_gate to find the top-K matches, then sparsely sums their value vectors. Same answer, much less compute.
What does INSERT/DELETE do to these matrices?
LARQL's mutation verbs add, remove, or modify rows of W_gate / W_up / W_down — without retraining. INSERT adds a new (key, gain, value) triple. DELETE zeros one out. UPDATE rewrites it. Patches stack on top of an immutable base vindex; COMPILE bakes them into a new standalone vindex.
