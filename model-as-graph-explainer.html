From Model to Graph

How LARQL turns a stack of transformer matrices into a queryable graph (the vindex).

W_gate row = key (only this is indexed for KNN)
W_up row = gain (multiplier in GEGLU)
W_down row = down vector (feature-major, rebuilt)
Subject → feature edge (Step 3)
Feature → object edge (Step 3)
Walk path through fired features (Step 4)
Step 1 · Stack of layers
A transformer layer is attention + FFN; LARQL targets the FFN half
Each transformer layer has two sub-blocks: attention (Q, K, V, O projections) and FFN (W_gate, W_up, W_down on modern gated architectures like Llama, Gemma, Mistral, GPT-OSS). LARQL doesn't turn the whole transformer into a graph — it decomposes only the FFN sub-block of each layer. Attention still runs as ordinary BLAS matmuls from the safetensors file, even on the walk path. The residual stream flows top-down through every layer, getting added to by attention and FFN in turn. Below: a 4-layer toy model with 4 features per layer, with the four phases that real models exhibit (passive embedding work, active syntactic processing, factual knowledge, and output formatting — see docs/findings.md §2). Real Gemma-3 4B has 34 layers and 10,240 features per layer.
Key idea: A transformer is attention + FFN, stacked. The (W_gate, W_up, W_down) shape is specific to gated FFNs — older architectures (GPT-2, BERT) only have W_in and W_out and don't have an addressable per-feature key vector. The gate matrix is what makes the graph view possible: each row gives feature i a "key" that an input can be matched against.
Step 2 · Each feature becomes a node
Flatten the matrices into a node list — but rebuild W_down first
Every feature index i at layer L picks out the same row of W_gate and W_up (both stored [intermediate, hidden]). The catch: W_down is stored transposed as [hidden, intermediate] in safetensors, so feature i is the i-th column — scattered with stride intermediate. LARQL's build_down_features tool rebuilds it as feature-major [intermediate, hidden] in down_features.bin, so each feature's down vector becomes 2560 contiguous f32s (10 KB on Gemma-3 4B). Only after that rebuild is "row i = feature i's value" true for all three matrices.
node(L, i) = { key: W_gate[L][i], up: W_up[L][i], down: W_down_feature_major[L][i] }
This is the walk graph — features as runtime traversal nodes. It's not the same as the persisted edge graph in Step 3, where the nodes are tokens and features are edge labels. Both views describe the same FFN; LARQL exposes both.
A node is (L, i) — the same index i at a different layer is a different node, because gate vectors are layer-specific (calibrated to each layer's residual space). On Gemma-3 4B that's 34 × 10,240 ≈ 348k nodes.

Only the gate vector is indexed for KNN/graph traversal — the up and down vectors are payload, fetched once you've decided to "visit" a node. up_features.bin is optional (built only when you want a full-mmap walk).
Step 3 · Each feature is itself an edge
Edges go token → feature → token, not feature → feature
The natural intuition — "feature i in layer L talks to feature j in L+1 when their value and key align" — is mathematically sensible (it's the FFN-FFN composition strength) but it's not how LARQL actually defines its edges. LARQL's nodes are tokens, not features. Each FFN feature becomes one (or a few) edges of the form (subject_token, L{layer}-F{feature}, object_token). The schema lives in crates/larql-core/src/core/edge.rs and docs/format.md.
subjects(L, i) = top-K tokens by dot(W_gate[L,i], E[token])
objects(L, i) = top-K tokens by dot(W_down[L,i], E[token])
edge = (subject, "L{L}-F{i}", object, confidence)
Two KNN sweeps per feature, both against the vocabulary embedding matrix E: project the gate vector to find the tokens that excite this feature (subjects), project the down vector to find the tokens it pushes toward (objects). Cartesian product → emit edges. Why this works: the residual stream lives in embedding space at the input, and modern transformers preserve that alignment well enough that gate and down vectors stay roughly readable in vocabulary space. Concrete edge from a real Gemma-3 4B vindex:
{ "s": "France", "r": "L26-F9298", "o": "Paris", "c": 0.89, "src": "parametric" }
High c_in × c_out → feature has a clear "trigger token" and a clear "output token." Strong, factual edge — usually late layers.
Diffuse projections → ~85% of features ("dark space") have down vectors that don't resolve to any single token. Structural computation, not entity knowledge.
The persisted edge graph: each FFN feature becomes ~K subject × K object edges between tokens. The example shows three real-style features and the edges they generate.
The graph wasn't trained — it was always there. 348k features → ~8M edges (each feature's top-K subjects × top-K objects). Confidence is per-layer-normalized, with two flavors: c (combined signal, biased toward structural edges) and selectivity (input specificity, biased toward factual edges). For knowledge extraction, filter on selectivity + late layers (L19–L29 for Gemma-3 4B).
Step 4 · Inference is a walk
An input traces a path through the graph
When a token enters the model, its embedding (scaled by √hidden_size on Gemma) becomes the layer-0 residual. Each layer runs attention then FFN, both reading from and adding to the same residual stream. The FFN's contribution is the graph walk:
1. score_i = dot(residual, W_gate[L,i]) for all i ← KNN ranks by this
2. pick top-K features by score (K ≈ 10 of 10,240)
3. up_i = dot(residual, W_up[L,i]) for the K picked
4. act_i = silu(score_i) * up_i ← GEGLU magnitude
5. residual += sum_k act_k * W_down[L,k]
Selection vs. magnitude: step 1's gate score is the only selection criterion — that's what makes it a graph walk (KNN on gate vectors). The silu(gate) * up in step 4 is the activation magnitude of an already-selected feature, not a re-ranker. (A feature with high gate score but near-zero up score still gets visited; it just contributes ~nothing.)

Two walks share the name. The conceptual graph walk is the sparse top-K version above — what makes "inference is a walk" a true sentence; it's the path used for WALK traces and the no-down-features fallback. The exact walk (the production fast path, 517 ms vs 535 ms dense) is mathematically dense — all 10,240 features participate — but reads the down projection from the feature-major down_features.bin mmap. Same arithmetic as dense FFN, better page cache. The boundary-sweep proof of "zero divergence at every layer" is for the exact walk; the sparse walk is an approximation.

Attention is the missing index. The FFN graph stores all knowledge; attention picks which features to activate for a given query. findings.md §6 reports that statically-extracted features and actually-activated features have ~zero overlap — attention routes "Germany" to features whose static subject keys are "französisch" / "немец" based on context.

Step 5 · The vindex is this graph, on disk
What LARQL actually stores
The vindex directory holds the graph in mmap-friendly form. Three extract levels gate which files exist: browse (~3 GB) gives you the FFN graph data; inference (~6 GB) adds the attention + embedding weights needed to run a forward pass; all (~10 GB) adds dense weight files needed for COMPILE to bake patches back into a new vindex. Filenames live in crates/larql-vindex/src/format/filenames.rs.
# top-level descriptor + provenance
index.json → per-layer offsets, dtypes, quantization, extract level
weight_manifest.json → checksums for upstream HF weights
tokenizer.json + configs → tokenizer + generation config

# browse level — graph data (FFN-as-graph)
gate_vectors.bin → node keys, layer-major (per-layer offsets in index.json)
down_features.bin → node values, feature-major [intermediate, hidden] per layer
down_meta.bin / .jsonl → per-feature metadata (top tokens, scores)
feature_labels.json → human-readable node labels
feature_clusters.jsonl → cluster assignments

# inference level — needed to run forward
embeddings.bin → token embedding matrix
attn_weights.bin → attention Q/K/V/O (with _q4 / _kquant variants)
norms.bin → RMSNorm scales
up_features.bin → feature-major up vectors (full-mmap walk)
knn_store.bin → optional HNSW graph

# all level — needed to recompile
gate_weights.bin / up_weights.bin / down_weights.bin

# patches (separate from base — overlay via PatchedVindex)
*.vlp → JSON overlays from INSERT / DELETE / UPDATE
Edge triples don't live in the vindex. The (France, L26-F9298, Paris, 0.89) triples from Step 3 are produced by weight-extract and stored in separate .larql.json / .larql.bin files (see docs/format.md). The vindex stores the vectors — the structural graph — and triples are a downstream materialization computed by KNN against the embedding matrix. Two views, same content, different files.
How does this enable LQL queries?
Three extraction levels gate which statements work: browse → DESCRIBE / WALK / SELECT, inference → +INFER, all → +COMPILE.

WALK FROM "cat" traces the activation path through layers — the orange path above.
SELECT * FROM features WHERE layer = 1 reads node metadata for one layer.
DESCRIBE FEATURE 1.2 shows the key / up / down vectors of node (1, 2).
INSERT FEATURE INTO 1 ... adds a new node — a (key, up, down) triple — without retraining. The mutation lands in a .vlp patch file, never the base vindex.
Because everything is mmap'd, queries are zero-copy. The graph is the file.
Why not store edges as adjacency lists in the vindex?
Two reasons. First, the conceptual feature(L) → feature(L+1) graph is dense: 348k nodes with ~10k potential outgoing edges each ≈ 3.5B candidate edges — and most of those interactions are mediated by attention in between, so they aren't stable across inputs. Second, the actually-defined edges (token → feature → token) are precomputed and stored — just not in the vindex. They live in standalone .larql.json / .larql.bin files (~8M edges per Gemma-3 4B model). The vindex stays as raw vectors; the triples view is a separate materialization that you can publish, query, and version independently.

At runtime, the walk still recomputes its top-K via gate KNN against the live residual rather than reading a pre-built outgoing list — that's why Walk FFN is sparse-by-design and (with the down-features mmap) faster than dense.
Why are base vindexes immutable?
It's a hard architectural invariant (see AGENTS.md): all mutations flow through PatchedVindex, which overlays a .vlp JSON patch on top of the readonly base. SAVE PATCH persists it. COMPILE CURRENT INTO VINDEX bakes patches into a fresh standalone vindex by hardlinking unchanged base files (APFS fast path) and rewriting only down_weights.bin column-wise where features changed. This makes vindexes safe to share, version, and stack patches on — the base is content-addressable and never mutated.
