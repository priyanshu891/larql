LARQL — From Model Weights to a Queryable Graph

A first-time-user's tour of how a transformer becomes a database, how that database is queried, and how edits get baked back into a model.

The one big idea. A transformer is already a giant tangle of numbers — billions of weights inside Wgate, Wup, Wdown. LARQL's claim is that those numbers already form a graph. Each row of Wgate behaves like a node ("this is the concept of capital city"), and the matching column of Wdown is what that concept writes back into the model — the outgoing edge. Extract doesn't change the model. It just files the same numbers onto disk in a layout you can query, walk, and edit. Compile bakes those edits back into a fresh standalone model.

Stage 1A model is just stacks of matrices

Every transformer block has the same skeleton. The part LARQL cares about is the feed-forward (FFN) sub-block, which is three matrices: W_gate, W_up, and W_down. For a 4B-param model like Gemma 3, each matrix is roughly 2,560 × 10,240 floats per layer × 34 layers.

That's it. The model is — quite literally — files of floating-point numbers on disk. A safetensors file is a labelled tarball of those matrices. LARQL's first move is to look at this and ask: what if these matrices were already a graph?

Stage 2Hidden inside the matrices is a graph

Here is the trick that makes everything else click. Look at one row of W_gate at one layer. It is a vector of 2,560 numbers. When the model runs, the dot product x · gate_row answers a single question: "how strongly does this hidden state look like the pattern this row encodes?"

If the answer is "strongly," the matching column of W_down at that layer gets added back into the residual stream. So each FFN feature is a tiny if/then:

if   x · gate_row[i]   is high     ←  the "node" — what to listen for
then add  down_col[i] · activation ←  the "edge" — what to write back

In a 4B model with 34 layers and 10,240 features per layer, that is roughly 348,160 nodes and far more edges (since each node connects to many tokens through its down-column). LARQL labels each node with a feature_meta entry — a guess at what the feature actually represents, derived by looking at which tokens its down-column most amplifies.

How does LARQL decide what's a node and what's an edge? It doesn't — the model already did. Every gate-row / down-column pair in every FFN layer is a node-with-an-edge-payload. LARQL's job is to file them so they can be looked up by name, by neighborhood, or by token, instead of being hidden inside a matmul.

Stage 3Extract files the graph onto disk

larql extract-index reads the model's safetensors and writes a vindex — a directory of memory-mappable binary files. No forward passes, no GPU, no fine-tuning. Just careful copying and re-layout.

There are three extraction levels, each pulling out a bit more of the model:

LevelDisk (Gemma-3 4B, f16)What it unlocks
browse~3 GBDESCRIBE, WALK, SELECT — explore the graph structure
inference~6 GB+ INFER — run forward passes against the vindex's FFN
all~10 GB+ COMPILE — bake patches into a standalone vindex

Anatomy of a vindex

The library analogy. A safetensors file is a single very long scroll: you can read it cover to cover, but you can't ask it "what's near Mozart?" A vindex is the same scroll, transcribed onto labelled cards in labelled drawers. gate_vectors.bin is the card catalog (concepts), down_features.bin is what each card writes when it fires, feature_meta.bin is the human-readable label on the card. Nothing was added or removed — just sorted.

Stage 4Query it like a database

Once a vindex exists, LQL (Lazarus Query Language) lets you talk to it like SQL talks to a relational database. Same data, three different lenses:

USE "output/gemma3-4b.vindex";

DESCRIBE "France";
-- "France" → entity feature L18:f7234, neighbors: Paris, French, Europe…
-- This is a graph lookup. No forward pass. ~5ms.

WALK "The capital of France is" TOP 10;
-- Token-by-token walk: at each layer, K=10 gate features fire, their
-- down-cols are summed into the residual. This IS a forward pass — but
-- it reads only the K features it needs from mmap, not the whole matrix.
-- Walk is faster than dense (517ms vs 535ms on Gemma 4B).

INFER "The capital of France is" TOP 5;
-- Full inference, returns top-5 next tokens with probabilities.
-- → "Paris" (0.87), "the" (0.04), "a" (0.02)…
Why walk can beat dense. A dense FFN multiplies the activation against the entire W_down matrix. The walk picks the K≈10 gate features that fired hardest and reads only those K columns from the memory-mapped down_features.bin. Same answer, less memory bandwidth, better cache behavior. The graph layout is the optimization.

Stage 5Edit it like a graph (but never overwrite)

The base vindex is read-only. Edits are stored as a patch, a small JSON file (.vlp) that overlays the base. INSERT, DELETE, and UPDATE auto-start a patch in memory; SAVE PATCH "name.vlp" writes it to disk.

USE "gemma3-4b.vindex";

INSERT EDGE "Mozart" -> "Composer" WEIGHT 0.85;
-- A new gate_row at the chosen layer + a new down_col, kept in the patch.
-- The base files on disk are still untouched.

DELETE EDGE "Pluto" -> "Planet";
-- Records a tombstone in the patch. The base entry is hidden, not erased.

SAVE PATCH "my_edits.vlp";
-- Persists the overlay. Base vindex is still readable by anyone else.
The acetate-overlay analogy. A patch is like the transparent acetate sheets old biology textbooks used — slip one over the page and a new layer of organs appears on top of the same body. Slip it off and the page is unchanged. Multiple acetates can stack. The base vindex is the printed page; .vlp patches are the overlays.

Stage 6Compile bakes a patch back into a model

Patches are great for experimenting, but at some point you want a self-contained model with the edits already inside. That is what COMPILE CURRENT INTO VINDEX "new.vindex" does: it produces a fresh vindex where the patch has been folded into the weight files, with no overlay needed.

The clever part is what doesn't get rewritten:

Base vindex (read-only)

gate_vectors.bin down_features.bin up_features.bin feature_meta.bin manifest.json
→

+ patch overlay (in memory)

gate_vectors.bin down_features.bin up_features.bin feature_meta.bin my_edits.vlp queries see base ⊕ patch
→

Compiled new vindex

gate_vectors.bin down_features.bin up_features.bin feature_meta.bin manifest.json ↪ hardlinked · ★ rewritten

Only the file that actually changed — down_features.bin — gets rewritten, column-by-column. Everything else is hardlinked to the base (an APFS / ext4 trick: same bytes on disk, two directory entries). A 10 GB vindex compiles in seconds, not minutes, even on a laptop.

The payoff. The compiled vindex is itself a vindex — same shape, no patch needed at load time. It can be loaded, queried, served via larql serve, or fed back into the next round of edits. The install_edge primitive that stamps a patched edge into gate/up/down tensors lives at crates/larql-cli/src/commands/extraction/compile_cmd/edge.rs — the lowest-level step of the COMPILE verb.

Glossary

vindex
A directory of memory-mapped files holding the graph form of a transformer's FFN layers.
gate vector
A single row of Wgate. Behaves like a node: a pattern the layer listens for.
down feature
The matching column of Wdown. The edge payload: what gets written when the gate fires.
feature_meta
A best-guess human label for each gate/down pair (e.g. entity:France).
extraction level
browse / inference / all — gates which LQL verbs are usable.
LQL
Lazarus Query Language — SQL-shaped surface for browsing, mutating, and recompiling a vindex.
patch (.vlp)
A JSON overlay carrying INSERTs / DELETEs / UPDATEs. Stacks on top of a read-only base.
walk
Sparse forward pass: K≈10 gate features fire per layer, only those K down-columns are read from mmap.
compile
Bake a patch into a fresh standalone vindex. Hardlinks unchanged files; rewrites only what changed.
install_edge
Lowest-level primitive that stamps a compiled edge into the gate / up / down tensors of the new vindex.
